I profiled these files and fixed them as far as they go in this round: commits `d392269` and `b61e558`.

**Where the time goes.** Not per-object full-surface work. Each shape covers ~14 000 px (the `bulk` bench shapes are ~100 px), so the 10k file composites **1.4 × 10⁸ pixels**, and the "400×" compared unequal pixel counts. Per pixel, sampling the paint and the graduated transparency cost ~21 ns, and each sample re-inverted the gradient's 3×3 mapping. The blend cost ~9 ns. Raster plus coverage was ~0.5 s of 4.7.

**A correctness bug found on the way (`d392269`).** Graduated transparency mappings stayed in document units while paints moved to device space, so every transparency gradient in these files rendered as one flat level. Four `transparency_graduated_*` goldens had been blessed from that bug and were re-blessed deliberately.

**Fixes (`b61e558`).** `PaintSampler`/`LevelSampler` ready each primitive once. Linear-affine gradients compute only `u`. No libm `fmod`/`round` per pixel. Opaque sampled pixels are written directly. `CpuConfig::deterministic` uses every core, which is byte-safe because bands merge by index and the determinism test proves it. Every fast path is pinned by a bit-exact test.

| file (100 %, `xarast-cli render`) | before | after |
|---|---|---|
| 10000GradFilledShapes | 10.2 s (8.1 s here) | **2.6 s** |
| 20000GradFilledShapes | 10.9 s | **2.2 s** |
| 20000GradFilledShapes50PCtransparent | 9.8 s | **4.5 s** |

**Why not within a small multiple of flat fills.** It is ~30 ns × 1.4–2.1 × 10⁸ pixels, spread over only three 1 MiB bands on a 766 px image. The remaining steps (row-wise/SIMD paint and blend, more deterministic bands) are filed as **XARA-T-0038**.
