Parallelism half done for **export** (commit f0a55c6, `render: add the banded export rasteriser on the CPU backend`). `xarast_render::export` renders through `CpuBackend::render_rows` with a band height that depends only on the output size: `export_band_lines(w, h)` aims for 64 bands, with a 16-row minimum and a 1 MiB maximum. A 766 px image is now 48 bands instead of 3. The output is byte-identical across runs, strip budgets and 1 vs 8 threads (`xarast-render/tests/export.rs`).

Measured with `xarast-cli export` at 96 dpi against `xarast-cli render`, same files, release build, machine under load 23–50:
- 10000GradFilledShapes: export 0.41–0.43 s, render 2.1–2.2 s
- 20000GradFilledShapes: export 0.57–0.89 s, render 3.8–4.5 s
- 20000GradFilledShapes50PCtransparent: export 0.36–0.66 s, render 2.0–2.3 s

Two things are left, and neither is in my crates:
1. The headless/on-screen `render` path still uses `CpuConfig::deterministic()` with 1 MiB bands (xarast-app `headless`). It could adopt `export_band_lines`, but the goldens would need to be checked or re-blessed first.
2. The per-pixel cost (~30 ns: paint sample + transparency sample + blend) is untouched.

So the acceptance criterion ("`xarast-cli render` ≤ 1 s") is met for export but not for `render`, and I am leaving this task open.
