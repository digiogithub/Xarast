Investigated on a quiet machine: 1-minute load 1.1 to 5.8, 24 cores, no other agents. Method: release `xarast-cli smoke-open` on the first walk, medians of 9 runs, with ProbeX16 as a no-bitmap control. For the bisect, each first-parent merge was built with `git archive | tar -x -m`.

**The slowdown is real, but only for Groucho2, and it comes from extra work rather than slower code.** Walk in ms, at 1fa7fef (the perf.md table) → 5e03b36 → after the fix:
- Groucho2 3.1 → 40.3 → **18.3**
- leafgirl 27.8 → 30.5 → **12.5**
- scope3 simple 23.1 → 25.9 → **18.4**
- Spitfire 8.9 → 13.9 → 12.4
- ProbeX16 (control) 197 → 196 → 203

**Bisect result:** 6ee21df, specifically b213986 ("xar: keep definitions found inside a dropped atomic subtree"). Groucho2 now imports 5 more bitmaps, 4 of them JPEG8BPP photographs. The first frame costs as much as the slowest bitmap. Here that is a 764×512 tag-71 image whose palette snap took ≈30 ms of its 34 ms decode: 125k cache misses, each a scan of all 256 entries. None of T-0221, US-0052, T-0218/T-0228 or T-0276 is involved. US-0053's `prepare` accounts for the +2.5 to 4 ms on leafgirl, scope3 and Spitfire, as perf.md already records.

**Fix (2b01544):** `snap_to_palette` now looks only at the candidates for the colour's cell, in a lazily built 16³ grid. The result is exact, ties included:
- A unit test checks it against brute force on palettes of 1 to 20k entries.
- The corpus exports all 73 PNGs byte-identical before and after.

Render time is unchanged.

**Other findings:**
- Spitfire's open went from 4.5 to ≈46 ms at 7f44eac. That is a one-time ≈41 ms font-service start (fontconfig) paid by the first document with text in a process; opening it again takes 3.8 ms.
- `build_scene`'s re-decode (T-0281) does not affect these walks. The fix is not about it.

**Gates:** fmt, clippy, workspace tests (1885 passed, 0 failed, 1 ignored, with the corpus), deny and `build --locked` all pass. perf.md and image.md are updated (38fcd2e).
