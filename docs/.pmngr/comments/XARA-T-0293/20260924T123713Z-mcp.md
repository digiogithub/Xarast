Report (branch claude/xara-xtreme-rust-port-ktggmu, commits e537e4a, de654bd, 8d04570; not pushed).

Design
- The walker exposes its single decode path: `walker::ready_image(res, budget)` (make_image + pyramid) and `walker::is_decodable(res)`. The walker's `decode_all` uses `ready_image` too.
- `DecodedImages::image_for(res, budget)`: a hit returns the filed image (or the filed failure). A miss decodes through `ready_image`, with a panic counted as a failure, and files the result. A resource with neither native pixels nor an encoded original is not filed, so the walker still counts it as pending.
- The gallery: `Thumbnails` jobs now carry the document's `DecodedImages` (`view` passes `session.decoded_images()`). The worker calls `bitmap_gallery::thumbnail(res, images)`: `image_for` under `PixelBudget::global()` (the budget the session's walkers use), then `shrink` over `ImageRef::level(0)`. That call brings an evicted base back in place (Materialise), on the worker thread only, never the UI thread. The copied dispatch `decode_straight` is gone.
- The thumbnail cache stays keyed by content hash and shared by all documents.

Tests
- `tests/gallery_thumbnails.rs` keeps the old dispatch as an oracle. Thumbnails are byte-identical on synthetic bitmaps (native, PNG, corrupt, empty) and on all 44 corpus bitmap records, whether decoded fresh or found in the session cache. So there is no difference to explain.
- `tests/decoded_images.rs`: opening the gallery on a walked document decodes nothing (+2 hits, decoded unchanged). A bitmap the gallery decodes first is not decoded again by the next walk (+1 decode in the gallery, 0 in the walk, +3 hits).

Not done, by choice: shrinking from a pyramid level instead of the base. It is cheaper for big photos, but it uses a different filter (linear light), so the thumbnails would change. Revisit it with the disk cache (T-0289).
