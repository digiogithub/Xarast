**Measured on the reference machine** (Intel Core Ultra 9 285, see `docs/memory/perf.md`), 2026-09-23, `cargo bench -p xarast-render --bench render -- display_list`, `bulk` scene at 1920×1080, warm scene, `DirtyRect::NONE`. Three runs, load average 6–13 from other agents:

| Nodes | Measured | per command | Budget |
|---|---|---|---|
| 20 000 | **1.11 ms** (1.11–1.26 across runs) | 55 ns | — |
| 100 000 | **20.8 ms** (20.8–21.7 across runs) | 208 ns | ≤ 3 ms → **6.9× over** |

The old estimate (10.6 ms, extrapolated linearly from 20k on the container) was too optimistic: build time is **superlinear**. 5× the nodes costs 18.8× the time. The loop in `DisplayList::build` is linear, so the likely cause is memory, not the algorithm: at 100k the `Vec<DrawCmd>` plus the `Arc` path clones no longer fit in cache, and each build allocates a large, fresh vector. That is a hypothesis, not yet profiled. Shrinking `DrawCmd` (boxing the stroke payload) works on both. Reusing the command vector between builds does too.

New bench group `display_list/build_{20000,100000}` added so the 100k number is measured directly from now on. Nothing is fixed in this round.
